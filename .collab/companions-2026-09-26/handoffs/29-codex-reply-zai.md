### Findings

- **F29-1** [minor] `plugins/codex-consult/scripts/codex-consult.ps1:5039`, `plugins/codex-consult/scripts/codex-consult.ps1:5493` - A machine-wide health update that fails for a reason other than a lock timeout (an unwritable path, a serialization or IO error inside Update-MachineHealth's catch) is neither retried at the ledger commit nor reported: the retry flag and the `machine-wide health not updated` warning are gated on MachineHealthLastError -eq 'lock timeout', so D2's promised 'a failed update is retried once ... if it still fails the run warns' holds only for lock timeouts. The repository ledger keeps the truth, so the impact is observability of a silently stale cross-repository health file. Trigger: The health file's directory becomes unwritable, or Write-TextAtomic/JSON serialization throws inside Update-MachineHealth during a run that records a provider failure. Evidence: read-code: $machineHealthRetry is set only when [string]$script:MachineHealthLastError -eq 'lock timeout'; read-code: the retry and the warning run only under $machineHealthRetry; a non-lock false return adds no warning. Verify: Make the health path read-only (not its lock), run a failing fake consultation, and inspect warnings[] and the file: no warning and no record, with exit 0/1 unchanged. Remedy: Set MachineHealthLastError for every failed Update-MachineHealth (e.g. 'write failed'), and gate the retry/warning on any non-empty last error, keeping the lock-timeout wording for that case.
- **F29-2** [note] `plugins/codex-consult/scripts/codex-consult.ps1:1181`, `plugins/codex-consult/scripts/codex-consult.ps1:1190` - Two -Kick callers on the same member can race on the acknowledgement: the second caller removes any existing .ack before writing its kick file, which can delete the ack the first caller is about to read; the first then reads an empty file, misses the '^late' marker and prints the 'stopped' message for a kick that was actually late. Both callers still exit 0 and the member consumes the kick exactly once, so only the reported wording can be wrong. Trigger: Two shells run -Kick -Member <NN> within the same ~10 s acknowledgement window on the same running member. Evidence: read-code: each caller removes the .ack up front, waits for it, sleeps 100 ms, reads and removes it; nothing serialises the two callers; inferred: only one ack exists per kick, so the second reader can observe an empty/deleted file. Verify: Launch two -Kick invocations 200 ms apart against one fake member whose turn finishes immediately; compare each caller's printed wording with the ledger's kick_late warnings. Remedy: Write the ack under a caller-unique name (or append and never delete), or have a caller that finds no readable ack fall back to the member's ledger outcome before choosing its message.
