## Framing

The design is closer to “add a third adapter” than “add a table row”: HEAD’s non-codex retry/repair paths and the argv contract are still agy-specific (findings #1-#2). Read-only is also being framed only as write safety. A scratch tree would not fix the other exposure: native `read_file` may still read outside the repository, and the contributor model’s training policy is a confidentiality decision, not a sandbox decision.

### Q1
Do not add a scratch workspace by default. It would weaken review fidelity (a copy can drift, and untracked/ignored files are easy to omit) while adding synchronization and quota cost. Keep the Muse preventive flags, run in the repository root, and retain the before/after evidence check. Document the real boundary: gitignored paths, submodules, and files outside the repository remain unmonitored; the launcher/updater can also write outside the tree. A stronger option is an OS-level read-only mount/container or disposable VM, but that is a separate, portable-infrastructure project. To choose, I would need Muse’s actual tool filesystem scope, updater behavior, and the threat model for secrets versus integrity.

### Q2
Refusing is the safer default. Better still, make the first version subscription-only and refuse both known API-key variables regardless of `-SkipPreflight`; API-key billing belongs in a Codex provider, not this engine. If coexistence is essential, do not merely delete two names: launch Muse with an explicit allowlisted child environment, preserve keys only for an explicit API-key entry, and record the sanitization. That avoids unknown future key aliases and surprise account selection.

### Q3
A local `auth.json` shape check is acceptable and preferable to spending one of only 10-50 prompts. Call it “credential file present,” not proof of validity; an expired token should fail on the real run and be classified auth. Also, keychain mode cannot be a mere warning in the current preflight model: it is `unknown` and is refused unless explicitly overridden. A non-consuming `muse auth/status` command, if one exists, would be better.

### Q4
Fragile parts are the MSP envelope/version, nested `stream` selection, `run.model.configured`, and the precise terminal payload. Parse semantics, not record luck: require a supported `schema_version`, one session stream with a UUID, terminal and session on that stream, exactly one terminal, and a configured model equal to the requested model. Map exit 2 and max-steps to explicit capability failures rather than leaving them `unknown`. Record a real CLI/MSP version using a non-billing command; optionally pin `muse-bin-<version>.exe` via `CODEX_CONSULT_MUSE_EXE`, and fail closed on an unsupported MSP version rather than silently trusting the auto-updating `muse.cmd`.

## Verified versus inferred

Verified at HEAD: engine table and adapter contract, argv construction, preflight/roster validation, endpoint fingerprinting, shared failure classifier, tree snapshots, retry/repair calls, panel propagation, provider listing, and test surface. Inferred from the brief or not covered by its probes: Muse resume session identity, version/auth subcommands, launcher behavior for paths with spaces or `%`, out-of-repository `read_file`, and whether every listed 1.2 model is subscription-eligible.
