The framing combines three different capabilities: provider routing, evidence requests, and comparative evaluation. They need not ship together. Unlisted options are: ship R7 first with manual comparisons; use explicit bridge-owned reviewer profiles instead of interpreting arbitrary Codex configuration; or implement groups as immutable review manifests rather than consultation tags. R8’s roadmap explicitly starts with a convention. To choose, I need representative configurations, expected group frequency, completed requested-check examples, and whether R9 promises descriptive reports or defensible model comparisons.

**Q1. Lineage.** Keep provider, model, endpoint/protocol identity, and harness provenance, but separate compatibility identity from audit metadata. A CLI patch upgrade should not automatically invalidate a thread; endpoint/protocol changes should refuse reuse. Canonicalize selected configuration values before hashing—comments and ordering should not matter; secret rotation should not split a lineage.

The proposed default is incorrect: omitting `-Provider` delegates routing to Codex, which may be configured for ZAI, while your ledger asserts `openai`. Resolve and pin the actual provider/model, or record unknown and forbid reuse. A partial TOML scanner must reject unsupported syntax rather than guess. Consider explicit profiles if full configuration resolution is too expensive.

Treat legacy provenance as unknown. Also stop treating the baseline’s “newest rollout” fallback as verified provenance: an unrelated concurrent session can acquire the current run’s lineage label.

**Q2. Effort.** The ZAI mappings are reasonable policy choices, not equivalent reasoning budgets. Make capabilities model-specific and independent of arbitrary provider aliases. Unknown providers should require a declared supported vocabulary or an explicit native-effort setting; automatic pass-through is unjustified. Record requested value, transmitted value, mapping version, and provider-confirmed value when available. “Effective” otherwise overstates what you observed.

**Q3. Requested checks.** Start with the roadmap’s convention unless actual usage justifies v2. If shipping the field, give requests stable bridge-assigned IDs and store completion records separately; no elaborate scheduler is needed. `related` currently cannot reliably name a finding created in the same response because its ID is assigned afterward. Support a typed local finding index, existing finding ID, or invariant reference.

A request needs shell/procedure context; completion needs request ID, tested revision, log reference/hash, exit status, observation, and completed/failed/skipped state. Permissions remain descriptive, never authorization to execute. Enforce the cap locally. Dispatch validation by explicit schema version; preserve that v1 did not support requests rather than interpreting absence as a considered empty list.

**Q4. Groups.** Tags and links are insufficient. Freeze a group manifest containing brief hash, source/artifact fingerprints, purpose, shared instructions, baseline findings, and member attempts. Reject incompatible inputs and enforce fresh threads. The current prompt automatically includes all open findings: sequential member two would see member one’s results. Freeze the baseline and keep member outputs outside subsequent members’ readable review inputs, or label the comparison non-blind.

Add canonical issue membership, validity adjudication, verification minutes, and explicitly estimated avoided rework with rationale. Existing `verified` means a fix was verified, not that a report was a true positive. Record failed attempts and unmatched reports. Relations should be idempotent, validated, and atomically persisted. Agreement can share reproduction work; it cannot lower the evidence standard.

**Q5. Peak hours.** Keep warning-only by default. Provider choice does not justify mandatory scheduling. Define boundary, overnight, missing/invalid schedule, and date-exception behavior; record the evaluated schedule/version and unknown separately from off-peak. `-OffPeakOnly` must refuse when eligibility cannot be established. A launch-time check cannot promise every request in a long consultation occurs off-peak; name that scope explicitly. Omitting credit estimates is an acceptable documented scope cut.

**Q6. Acceptance gates.** I would HOLD until fixtures and live logs demonstrate correct configured-default identity; alias/model effort handling; harmless configuration edits preserving reuse; endpoint changes and unknown/cross-lineage parents refusing reuse; no adoption of unrelated rollouts; fenced v1/v2 validation and raw preservation; missing usage remaining unknown; stable check references and completion evidence; identical blind group inputs despite sequential execution; drift rejection; duplicate links without double-counting; recovery without lost relations; and schedule boundaries, invalid schedules, and exceptions. Include PS5.1/7 coverage. One successful GLM reply proves only the happy path.
