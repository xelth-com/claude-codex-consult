## Framing: options not listed
**A** Manual relay: pack->clipboard, reply<-clipboard; a human carries both ways. Covers sites with no adapter; the brief never considers the human already in the loop.
**B** Read-only extraction: the user sends; the extension only reads the answer into the ledger. Drops `send`/`new_chat`/`attach`.
**C** Sanctioned routes first: `agy` already covers the cited Gemini account; the new capability is grok.com free.
**Need:** store or sideload (decides MV3 legality of fetched adapters and signing); acceptance of the 'debugger attached' infobar (trusted input needs `chrome.debugger`); are prose-only replies acceptable; in-writing acceptance of *account* ban risk; PowerShell parity or C3 only; per-site turn quota.
## Q1 - Boundary
Ship nothing site-identifying: no domain in host permissions, no selector, no doc naming a site, empty catalogue. No `cookies` permission, no credential read, no CAPTCHA/anti-bot code, no self-patching selector repair (site logic by another name). Catalogue = signed pointers, never code: `{id, site, contract_version, sha256, signer, url}`. Signing = publisher keys with a user-pinned trust set (TOFU); a project CA makes the company the distributor again. Precedent: userscript managers ship and host no scripts; directories list user code by hash only. gemini-mcp already says it: automated use of the consumer web app is contrary to Google's terms; the program is a personal client for the user's own account. Reuse it in README, licence and per-adapter consent.
## Q2 - Shape
Declarative JSON adapter first (selectors, timing, status - data), WASM second, in the user's own tab: JSON is hashable and cannot exfiltrate. Disqualified: an outside CDP/Playwright driver - profile dir or debug port means credential exposure, hidden from the user. `chrome.debugger` is the only trusted-event path; its infobar shows the user every turn. WASM's real sandbox is the JS host API (the module cannot touch the DOM), so that API is the artifact: per-tab, DOM read/click/type, no `fetch`, no `chrome.*`, no cross-tab.
The five verbs carry no identity, failure class or completion boundary. Minimum: `id/site/contract_version/dom_signature`; `probe() -> ok|logged_out|rate_limited|gate|dom_changed`; `new_chat()`; `send(text)`; `await_answer(timeout) -> {text, complete}`; `limits() -> {max_input_tokens, max_turns, min_interval_ms, thread_continuable}`. Drop `attach` in v1; `complete` catches a truncated read.
## Q3 - Detection
Also: hard-stop and retire the adapter version on any gate or limit signal; never auto-dismiss a CAPTCHA-shaped dialog; one site, one tab, strictly sequential (parallel fan-out is a correlated footprint); mandatory per-run token and Origin check on the loopback WS (127.0.0.1 is treated as trustworthy, so any page can open it; gemini-mcp ships the token off); jittered delays; refuse to run unless the tab is visible and focused, making 'user sees every turn' enforceable; no scheduled runs; name the user's account risk, not just the product's.
## Q4 - Quality
Make the per-adapter budget a first-class engine bound (C3 already fails 'brief too large for this engine'): default ~4-8k tokens, asserted not estimated. Free tiers cap turns, so `-FormatRetry` repair is a second real message - default repair off for `browser`, every turn counted against quota and ledger. No repo tools means read-only class, lowest router band until N rated consults, `findings_unavailable` for prose-only. Continue the site thread only when `limits().thread_continuable` and the adapter can name it; else stateless re-send as `http` does.
## Q5 - Telemetry
`adapter_id`, `adapter_version`, `site_domain`, `contract_version`, `outcome_class` (answered | prose_only | gate | rate_limited | dom_changed | login_required), `turns_used`, `repair_used`. `outcome_class` makes retirement computable. Aggregate per `(adapter_id, contract_version)`, else a dead version's score inherits into its successor. Ship an empty catalogue; updates opt-in, user-initiated, hash-verified, landing disabled; the retract list advisory, locally overridable - a remote kill switch is remote control.
## Q6 - Order
(0) Manual relay plus a written boundary/refusal policy. (1) A user-written spike on one site: does human-cadence driving survive a week without a gate? If not, build nothing else. (2) Declarative schema, host API, authenticated relay, read-only mode. (3) Telemetry and the per-adapter table. (4) A user-land reference adapter in a separate repo. (5) WASM last. Do not build: any adapter here; runtime-fetched code; stealth; CAPTCHA handling; `attach`; scheduling; panel fan-out; PowerShell parity.

A Chrome Web Store extension may not fetch and execute code at runtime under the MV3 remotely-hosted-code policy; if the product ships through the Store, this channel can get it delisted, and a runtime-fetched WASM is the same violation as eval. Trigger: A user enables an adapter whose bytes are downloaded after install (or the channel pushes an update) in a Store-installed build. Not verified in this session. Verify: Confirm the extension distribution channel and read the current Chrome Web Store policy clause on remotely hosted code and WebAssembly; then decide fetch-at-runtime vs user-supplied local file vs sideloaded build. Remedy: Decide the channel first. Either (a) sideload/unpacked distribution, where the policy is not enforced, and ship adapters as user-supplied local files only, or (b) Store distribution with zero runtime code fetch: adapters must be unpacked locally by the user and imported through a file picker, and the 'update channel' degrades to a signed pointer list the user acts on manually.
