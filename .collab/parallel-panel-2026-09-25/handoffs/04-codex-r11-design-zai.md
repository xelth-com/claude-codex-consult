## Framing

The design keeps "a member = today's run minus the task lock". Options it does not list: per-member store fragments merged by readers (no shared mutable stores); an append-only journal instead of whole-file replaces; parent-staged ordered commit (Q1). To choose I'd need to know: how often commits really contend (a commit is milliseconds, so the write lock is nearly free); whether R12's non-blocking mode reuses the parent/child split (if yes, member-owned commits pay twice); and whether `codex-findings.ps1`/hook writers can move in the same wave — they must, or the write lock is theater (finding #3).

## Q1 — re-read + re-apply vs parent-ordered commit

Re-read + re-apply is sound and I prefer it: ids are deterministic (`F<NN>-k` from `Nn` + reply order, codex-consult-common.ps1:1317-1320), reviewer_checks append without ids, and a dead member loses only itself. A parent-ordered commit makes the parent the single point of failure after members already paid for their replies, and drags reply validation into the parent. Conditions: every store writer must use the one re-read+re-apply path (findings #3, #4); the early ingest that renders the handoff section must be recomputed on the fresh store and asserted equal (the design says this — keep it); and the 60 s give-up path must not itself need the write lock (finding #2).

## Q2 — agy residual

Acceptable only after fixing the temp-file hole (finding #1): the residual (a concurrent agy reviewer editing the task's stores undetected) is narrow and the commit's re-read refuses an unparseable store. A cheap tightening: treat the two stores as allowlisted-diff — the after-state must parse, and every added consult/finding must attribute to this panel's n/NN set from the spec; anything else still fails.

## Q3 — parent death

"A new run refuses while any member record is active" is not enough as stated: `reserved` is always inactive (common.ps1:4755) and a `running` record whose reviewer exited reads inactive during the commit window, so after parent death a new run can start on the task while an orphaned member still runs (finding #4). Members should not stop — their replies are good — but they must own their record (rewrite it with the member pid; a live writer pid keeps it active; add a `committing` state) and re-check parent liveness just before `launching` (codex-consult.ps1:1937), aborting cheaply there. Mark such entries `panel.orphaned`.

## Q4 — default concurrency

All-at-once is fine only when members sit on distinct sign-ins. The roster permits two entries on one label/engine (common.ps1:3761) and agy members share one sign-in; simultaneously launched members all preflight before any sibling failure is committed (each reads all ledgers at its own start, codex-consult.ps1:1086), so same-plan members duplicate a quota/auth failure. Default: all-at-once, but cap per engine (agy → 1) or stagger launches so later members see earlier failures. To decide: whether the CLIs serialize internally (locks in their homes) and whether plan limits are per-request or per-connection.

## Q5 — append-order assumptions

Verified: `Select-ParentThread` (common.ps1:4245) and `Find-ThreadEntry` (4183) scan the array from the end — sorted-by-n insertion keeps "last = highest n" true, so keep the array sorted by n, never by finish time. `Get-EndpointHealth` sorts by recorded `when` (3710), position-independent. `codex-findings` -List/-Stats and the scoreboard aggregate by n/id — order-independent. No blocker.
